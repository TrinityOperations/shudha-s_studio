2. PRODUCT SUMMARY
==================
Shudha's Studio is a Melbourne-based personalised-gift maker. The application is one Next.js deployment with two parts:

A. Public website
- Content-driven portfolio/storefront, not traditional e-commerce.
- Visitors browse examples of personalised products.
- No public prices, cart, checkout, or online payments.
- Conversion goal is an appointment/consultation booking.
- Later v1 scope includes a custom-order wizard, browser-only wishlist/mood board, customer gallery, English/Bengali UI, and seasonal themes.

B. Private owner dashboard at /admin
- Intended for one non-technical owner, primarily on phone or laptop.
- Manages products, images, taxonomy, bookings, availability, content, testimonials, gallery moderation, themes, insights, and PWA notifications.
- Current authorization model is a single Supabase Auth user whose email equals OWNER_EMAIL case-insensitively.

Business context from the SRS:
- One-person studio, started around late 2024.
- Approximately 3.2K Facebook followers at specification time.
- Instagram: shudhas.studio.
- Typical products include mugs, apparel, home decor, keyrings, cushions, stationery, and gift packs.
- Bengali text, Bengali cultural themes, and Islamic calligraphy are important.
- Customer base is largely the Bangladeshi community in Melbourne.
- Orders were historically taken via Messenger.

Explicit v1 exclusions:
- Online payment.
- Cart/checkout.
- Shipping workflow.
- Multi-vendor support.
- Customer accounts.

Absolute invariant: THERE ARE NO PRICES ANYWHERE in public UI or the data model. Quotes happen during consultation.

6. ARCHITECTURAL RULES — MUST FOLLOW
====================================
Mutations:
- All mutations belong in server actions under src/actions/.
- Standard action order: validate with shared Zod schema; requireOwner() for admin actions; perform write; revalidate relevant paths; return ActionResult.
- Validation errors and action errors are i18n keys, not English prose.
- Never call the database from a client component.
- Public actions must verify Turnstile and should be rate-limited where required.

Reads:
- Put reads in src/db/queries/, generally one entity/domain per file.
- Call them from server components or server-only code.
- Do not put inline SQL/database reads in pages.
- Public product queries must explicitly return published products only. Admin queries may access all statuses.

Admin protection:
- src/proxy.ts is only the first gate.
- The admin dashboard layout calls requireOwner().
- Every individual protected admin page must call requireOwner() because pages can render independently of layouts.
- Every admin server action must call requireOwner().
- OWNER_EMAIL comparison is trimmed and case-insensitive.
- Client-side checks are cosmetic, never authorization.

Forms:
- React Hook Form + zodResolver + shared schema.
- Use shadcn Field components and shared FieldMessage.
- Server action validates the same data again.
- Show inline field errors and a Sonner success toast.
- All public forms include TurnstileField and server verification.

i18n:
- Every user-visible string must be passed through t('key'), including admin text.
- Flat JSON keys in src/lib/i18n/en.json and bn.json.
- Server: const t = await getT().
- Client: const t = useT().
- Bengali dictionary falls back per key to English.
- Locale is cookie-persisted; no /bn route prefix.
- Slice-specific i18n namespaces are defined in slice cards.
- Add keys alphabetically to both dictionaries; do not rename/delete unrelated keys.
- Bengali content is stored in sibling *_bn columns rather than a translations table.

Images/storage:
- Use next/image for rendered images.
- Prompt for alt text on upload; English alt is required, Bengali alt optional.
- Product images are processed to WebP, max 1600px full image plus 400px thumbnail.
- Browser downsizing targets max 2000px before upload to stay below Netlify function body limits; PNG transparency is preserved and other large images become JPEG client-side.
- Server still validates and re-encodes with Sharp.
- next.config.ts allows a 12 MB server-action body.
- Do not hand-roll a second image/storage pipeline; reuse existing helpers.
- Public buckets: product-images, site-images, gallery-images.
- Private buckets: gallery-pending, booking-uploads.
- Gallery submissions remain private until approval, when files are copied to gallery-images.

Time:
- Store timestamps in UTC.
- Display and calculate availability in Australia/Melbourne.
- Use src/lib/time.ts and date-fns-tz.

Accessibility/performance:
- Semantic markup, labels, focus indication, keyboard operation, accessible dialogs/galleries.
- Respect prefers-reduced-motion globally and in component animation.
- Target Lighthouse accessibility >=95 and performance >=90 on mobile.
- Mobile-first from 360px upward.

Database/migrations:
- src/db/schema.ts is the schema source of truth.
- Use pnpm db:generate for normal schema changes.
- Constraints Drizzle cannot express belong in custom migrations.
- Never use drizzle-kit push because it could conflict with custom database constraints.
- Never hand-edit drizzle/meta snapshots.
- Migrations are serialized across branches and should only be run against the developer's personal Supabase project.

Generated UI:
- Do not hand-edit src/components/ui/*.
- Use the shadcn CLI to add/update primitives.

Decision log:
- Append a dated line to docs/DECISIONS.md for any non-obvious technical choice, library, pattern, or trade-off.


7. AUTHENTICATION AND SECURITY MODEL
====================================
Current owner model:
- Supabase email/password authentication.
- Only a user whose Supabase email equals OWNER_EMAIL can enter admin.
- No application users table and no helper roles yet.
- signIn first validates input, verifies Turnstile with optional x-forwarded-for IP, rejects non-owner addresses using the same generic invalid-credentials error, then calls Supabase signInWithPassword.
- Safe local next paths may be honored after login; external redirect URLs are rejected by validation.
- signOut clears Supabase auth and redirects to /admin/login.

Proxy behavior:
- Matches /admin/:path*.
- Refreshes Supabase session cookies.
- Calls Supabase getUser() on each admin request.
- Non-owner requests are redirected to /admin/login?next=<original pathname>.
- Signed-in owner visiting /admin/login is redirected to /admin.

Defense in depth:
- requireOwner() is the real server authorization check.
- RLS is enabled on every table with no anon policies.
- Supabase anon credentials are used for Auth, not table data.
- Service role is server-only and used for storage administration.
- Turnstile is mandatory on all public forms, including login.
- Booking conflict protection ultimately relies on a PostgreSQL exclusion constraint.

Known incomplete security requirements:
- General public form rate limiting is required by PW-38/NF-05 but is not yet broadly implemented.
- Magic link, forgot-password flow, optional 2FA, and explicit session-timeout UX are not implemented.
- Role support is only a C-priority future requirement.


8. DATABASE CONNECTION AND TLS
==============================
Runtime:
- src/db/index.ts uses drizzle-orm/node-postgres and pg.Pool.
- DATABASE_URL points to Supabase transaction pooler port 6543.
- Pool default max is 10; DB_POOL_MAX can lower it per Netlify process/function instance.
- Pool is reused through globalThis during development hot reload.
- Timeouts: idle 20 seconds, connection 10 seconds.
- TLS verifies against certs/supabase-ca.crt with rejectUnauthorized: true.
- Missing CA file throws; there is no insecure fallback.

Migrations:
- DIRECT_DATABASE_URL should point to session pooler port 5432.
- drizzle.config.ts can derive port 5432 from a 6543 DATABASE_URL if DIRECT_DATABASE_URL is missing.
- Credentials are split into host/port/user/password/database because drizzle-kit ignores ssl when a URL field is used.
- Migration TLS uses the same verified CA.

Reason for pg driver:
- The project switched from postgres.js because query pipelining/queue behavior could hang with Supabase transaction pooling. node-postgres queues excess queries client-side.

16. BOOKING ENGINE DESIGN (PLANNED, SCHEMA READY)
=================================================
The future booking engine belongs under src/lib/booking/.

Required flow:
1. Owner sets weekly rules, slot duration, buffer, booking horizon, minimum notice, consultation types, and blocked periods.
2. Pure functions generate candidate slots in Australia/Melbourne, including daylight-saving behavior.
3. Remove past, blocked, outside-horizon, and conflicting slots.
4. Public UI submits chosen slot/contact details/product/message/reference image.
5. Server never trusts the client slot; it recomputes availability.
6. Create booking within a transaction.
7. Convert exclusion-constraint collision into a translated "slot just taken" failure.
8. Later hook invokes email and push notification services.

Suggested defaults until client confirms:
- Monday-Saturday 10:00-18:00.
- 30-minute slots.
- Four-week horizon.
- 24-hour minimum notice.

Reference images belong in private booking-uploads and should use signed URLs for owner viewing. Never persist signed URLs.


17. I18N DETAILS
================
Locales: en and bn; default en.
Cookie name: locale.

Root layout:
- Reads locale server-side.
- Sets html lang.
- Loads Geist and Noto Sans Bengali.
- Supplies messages through I18nProvider.

Dictionary behavior:
- en.json is the complete reference dictionary.
- bn.json may omit keys and falls back per key to English.
- Tests ensure Bengali does not contain orphan keys and English values are non-empty.
- Translator supports {param} interpolation and returns unknown keys visibly rather than crashing.

Content localization:
- Prefer Bengali content when locale=bn and a *_bn value is present.
- Otherwise fall back to English.
- Product form already includes Bengali title, description, material notes, personalisation notes, and image alt support.


18. IMAGE AND STORAGE DETAILS
=============================
Product upload constraints and behavior:
- Client may downscale large phone images before FormData submission.
- Server action receives repeated files/alt/altBn fields aligned by index.
- Shared validator enforces count, image MIME, size, product UUID, and required alt text.
- Processed full and thumbnail files use UUID-based paths under product-images/<productId>/.
- Database stores paths, dimensions, and order.
- Reorder input must contain exactly all image IDs for the product.
- Duplicate product copies each storage object to independent paths.
- Single/bulk product deletion removes storage objects before deleting DB rows; storage failure aborts DB deletion.

Gallery future flow:
- Strip EXIF location information during processing.
- Upload pending files only to gallery-pending.
- Owner approval copies to gallery-images and fills public paths.
- Public query only returns approved rows.
